# PMI — нагрузочный тест

`PMI_LOAD_TEST=1 npx vitest run tests/load/central-load.test.ts` (Docker обязателен; параметры `PMI_LOAD_MEMORIES`, `PMI_LOAD_CLIENTS`, `PMI_LOAD_SECONDS`).

Сценарий: Postgres 17 + pgvector, 100 000 записей памяти одного проекта, 20 одновременных клиентов 30 секунд, смесь запросов: 40 % `POST /context` (задача + файл), 30 % hybrid `POST /search`, 20 % `POST /sync/push` (пакет из 10 записей), 10 % `GET /changes`. Проверяется отсутствие ошибок и p95 по бюджетам: context ≤ 1500 мс, search ≤ 500 мс, push ≤ 1000 мс, feed ≤ 500 мс.

## Результаты (MacBook, Docker Desktop, 2026‑10‑31)

| Версия | Запросов/с | context p50 / p95 | search p50 / p95 | push p50 / p95 | feed p50 / p95 | Ошибки |
|---|---|---|---|---|---|---|
| До исправлений | 3 | 12 488 / 15 547 мс | 2 948 / 3 501 мс | 239 / 582 мс | 28 / 58 мс | 0 |
| RLS один раз на запрос + ограниченные выборки кандидатов | 86 | 88 / 117 мс | 32 / 47 мс | 632 / 2 382 мс | 7 / 37 мс | 0 |
| + позиции ленты назначаются в конце транзакции | **115** | **252 / 358 мс** | **102 / 156 мс** | **182 / 253 мс** | **26 / 57 мс** | **0** |

Во второй строке чтения быстрее, потому что записи стояли в очереди на блокировке счётчика ленты; в третьей все виды запросов идут параллельно, поэтому пропускная способность выше, а задержка чтения выросла до реальной под полной нагрузкой.

## Найденные узкие места

1. **RLS на каждую строку.** Политики вызывали `core.project_role_of()` для каждой строки — полный просмотр таблицы и миллионы вызовов функции. Миграция `0007`: набор проектов пользователя вычисляется один раз на запрос (`core.project_ids_with()` как InitPlan), строки сравниваются через `= ANY`, индексы снова работают. Правила доступа не изменились (TEST 9 и тесты RBAC проходят).
2. **Кандидаты для контекста.** Один запрос с `OR` по всей таблице заменён объединением ограниченных выборок по индексам (совпадения поиска, файлы задачи, компоненты, последние записи); добавлены индексы `(project_id, updated_at)`, `(project_id, lower(component))`.
3. **Блокировка счётчика ленты при push.** Номер позиции брался на первой записи пакета, и блокировка держалась до конца транзакции. Теперь номера назначаются одним шагом в конце; порядок фиксации по‑прежнему совпадает с порядком ленты (читатель не пропустит позицию, зафиксированную позже).
