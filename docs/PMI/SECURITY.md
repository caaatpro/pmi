# PMI — безопасность: модель угроз и итоги проверки (Phase 10)

## 1. Что защищается

| Актив | Где | Угроза |
|---|---|---|
| Память проекта (решения, архитектура, код в снимках) | Postgres, том blobs, SQLite разработчика | Чтение посторонними, подмена, утечка секретов |
| Токены доступа | `~/.pmi/credentials.json` (0600), `core.api_tokens` (только SHA‑256) | Кража, подбор, отправка на чужой сервер |
| Рабочие копии разработчиков | диск разработчика | Запись вне рабочей копии при restore, перезапись свежих правок |
| Аудит | `core.audit_log` | Изменение задним числом |

## 2. Механизмы

| Требование ТЗ §14 | Реализация |
|---|---|
| Аутентификация | Персональные токены `pmi_pat_` (256 бит), в БД — только SHA‑256; срок действия, отзыв, отключение пользователя; ограничение неудачных попыток (429) |
| RBAC | `authorize()` — единственная точка в сервисе (DATABASE.md §4); роли организации и проекта, команды |
| Изоляция проектов | Postgres RLS на всех таблицах данных под ролью `pmi_app` и `app.user_id`; невидимый проект — 404 |
| Защита API | zod‑валидация, лимиты тел (16 MiB JSON, 64 MiB blob), тайм‑ауты заголовков/запросов, заголовки `nosniff`/`no-store`/`DENY`/`no-referrer` |
| Аудит | `core.audit_log`, приложению запрещены `UPDATE/DELETE/TRUNCATE`; содержимое памяти в аудит не пишется |
| Доступ к сессиям | состояние сессии и checkpoints — developer+; запись — только владелец и держатель аренды; принудительный resume — maintainer, в аудит |
| Защита рабочих копий | restore по умолчанию в новый worktree; in place — только чистая копия на том же коммите; файл, отличающийся от базы снимка, не перезаписывается |
| Шифрование соединений | Caddy (TLS); клиент отказывается слать токен по HTTP на нелокальный адрес |
| Хранение секретов | секреты не попадают в память (фильтр при записи, сервер отклоняет записи с ключами), снимки исключают `.env`, ключи, файлы с учётными данными; blobs шифруются AES‑256‑GCM |
| Защита знаний от несанкционированного изменения | агент не может подтвердить знание; синхронизация не меняет `confirmed`; подтверждение и deprecate — явное действие человека, в истории версий и аудите |
| Веб‑интерфейс | токен в заголовке, без cookies (нет CSRF); CSP без inline‑кода и внешних ресурсов (стили Mantine — по nonce на каждую загрузку), React экранирует все значения; права проверяет сервер ([WEB_UI.md](WEB_UI.md) §4) |
| Без Chain of Thought | Session State содержит только явно записанные шаги, решения и проблемы; транскрипты не синхронизируются |

## 4. Остаточные риски

- **Суперпользователь Postgres обходит RLS.** В Compose приложение подключается владельцем базы; запросы к данным идут под `pmi_app`, но в продакшене роль сервера не должна быть суперпользователем (DATABASE.md §4).
- **Аудит неизменяем только для приложения**: администратор БД может его изменить. Для внешней неизменяемости — экспорт `core.audit_log` в WORM‑хранилище.
- **Содержимое восстановленной рабочей копии** — чужой код (например, `.envrc`, скрипты npm); он попадает в отдельный worktree и не исполняется PMI, но исполнится, если разработчик запустит его сам.
- **Память и метаданные в Postgres не шифруются на уровне приложения** (только blobs); используйте шифрование диска/тома.
- **Токен в браузере** (веб‑интерфейс) хранится в `sessionStorage`, при «Запомнить» — в `localStorage`; успешный XSS мог бы его прочитать. Защита — CSP и вывод данных только как текст (React, без `dangerouslySetInnerHTML`); «Запомнить» — только на личном устройстве.
- **Токены без срока действия** допустимы (`issue-token` без `--days`); политика — выдавать с `--days` (OPERATIONS.md, чек‑лист).
