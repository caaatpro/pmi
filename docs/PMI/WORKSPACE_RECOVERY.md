# PMI — Workspace Recovery

Статус: **проект на согласование** (Phase 2). ТЗ §8.

Цель: незакоммиченное (и незапушенное) состояние рабочей копии разработчика A восстанавливается на машине разработчика B **побайтно**, ни один файл не теряется, ничьи более свежие изменения не перезаписываются.

## 1. Сравнение вариантов

| Механизм | Плюсы | Минусы | Роль в PMI |
|---|---|---|---|
| Git Stash | Нативно, учитывает staged/untracked | Локален, не переносится между машинами; `stash` меняет рабочую копию | Не используется для хранения. Используется только приём `git stash create` (создаёт коммит‑объект без изменения рабочей копии) для сбора tracked‑изменений |
| Git Branch + push (WIP‑коммиты) | Переносится через remote | Требует push‑прав, засоряет общий репозиторий, раскрывает незавершённое, ломает историю | Опция `--via-branch` для команд, которые этого хотят (§9) |
| Patch storage (`git diff --binary`) | Компактно, переносимо, читаемо | Зависит от base‑коммита; untracked не попадают | Основа для tracked‑изменений |
| Workspace Snapshot (файлы целиком) | Не зависит от git‑истории, точное восстановление | Объём | Для untracked и как резерв для tracked |
| Incremental snapshots (content‑addressed) | Повторно передаётся только изменившееся | Нужен GC | Да — все тела файлов как blobs по SHA‑256 |
| Git Worktree | Изоляция задачи, восстановление без риска для текущей работы | Место на диске | **Целевая точка восстановления по умолчанию** |
| `git bundle` | Переносит локальные коммиты без push | — | Для незапушенных коммитов |

**Выбрано:** snapshot = манифест + content‑addressed blobs, где для каждого файла хранится **полное содержимое** (а не только diff), плюс binary‑patch относительно base для проверки и наглядности, плюс `git bundle` незапушенных коммитов. Восстановление — по умолчанию в новый git worktree.

Почему полное содержимое, а не только patch: patch не применится, если у получателя другой base или файл бинарный/огромный; полное содержимое гарантирует «ни один файл не теряется». Content‑addressing делает это дешёвым: неизменившиеся файлы между snapshot не передаются повторно.

## 2. Что входит в snapshot

| Часть | Как собирается |
|---|---|
| `base_commit` | `HEAD` |
| `remote_base` | ближайший предок HEAD, существующий в каком‑либо remote (`git merge-base` с remote‑ветками / `git branch -r --contains`) |
| Незапушенные коммиты | `git bundle create - remote_base..HEAD` → один blob |
| Tracked‑изменения (staged + unstaged) | `git diff --binary HEAD` (patch, для проверки) + список `git status --porcelain=v2 -z` + полное содержимое каждого A/M/R файла |
| Staged‑состояние | `git diff --binary --cached HEAD` — отдельный patch, чтобы восстановить индекс |
| Удалённые файлы | запись `{path, status: D}` |
| Untracked, не игнорируемые | `git ls-files --others --exclude-standard -z` → содержимое |
| Права файлов, симлинки | mode из `git ls-files -s`/`lstat`; симлинки сохраняются как цель |
| Подмодули | только их HEAD и dirty‑флаг (рекурсивно — нет, предупреждение) |

Не входит по умолчанию: игнорируемые файлы (`.gitignore`), файлы > `PMI_SNAPSHOT_MAX_FILE` (50 MiB), каталоги `node_modules` и т. п. — они перечисляются в манифесте в разделе `excluded` с причиной. «Не теряется» означает: всё, что видит git, восстанавливается; всё исключённое явно перечислено.

## 3. Манифест

```json
{
  "schema": 1,
  "id": "01JD…",
  "parent": "01JC…",
  "projectId": "…", "repositoryId": "…", "sessionId": "…",
  "createdAt": "2026-10-31T12:00:00Z", "createdBy": { "user": "…", "device": "…" },
  "git": {
    "head": "abc…", "branch": "feature/x", "remoteBase": "def…",
    "bundle": { "sha256": "…", "commits": ["abc…", "…"] }
  },
  "files": [
    { "path": "src/a.ts", "status": "M", "mode": "100644", "sha256": "…", "size": 1234, "baseBlob": "<git blob id в base>", "staged": true },
    { "path": "src/b.ts", "status": "D", "baseBlob": "…" },
    { "path": "notes.md", "status": "U", "mode": "100644", "sha256": "…", "size": 88 },
    { "path": "src/new.ts", "status": "R", "oldPath": "src/old.ts", "sha256": "…" }
  ],
  "patches": { "worktree": "<sha256>", "index": "<sha256>" },
  "excluded": [ { "path": ".env", "reason": "secret" }, { "path": "big.bin", "reason": "size" } ],
  "totals": { "files": 4, "bytes": 1322 }
}
```

`manifest_sha256` — SHA‑256 канонического JSON (сортированные ключи). Поле `baseBlob` — id git‑объекта файла в base: по нему при восстановлении определяется, что файл у получателя не изменился с base.

## 4. Хранение и передача

- Локально: `~/.pmi/blobs/<aa>/<bb>/<sha256>` (zstd‑сжатие при записи, хэш — от несжатого содержимого), индекс в SQLite `blobs_index`.
- Сервер: blobs < 256 KiB — `work.blobs.data` в Postgres; крупнее — каталог тома `/data/blobs` (S3‑адаптер — позже через тот же интерфейс, переиспользуя `object-store` из `src/sync/adapters`).
- Загрузка: `POST blobs/missing` → `PUT` только отсутствующих → регистрация манифеста. Сервер проверяет SHA‑256 каждого тела и наличие всех blobs манифеста (иначе 412). Это и есть инкрементальность.
- Офлайн: snapshot создаётся и хранится локально; регистрация на сервере — через outbox.

## 5. Восстановление

```
pmi workspace restore <snapshot> [--worktree <path> | --in-place] [--dry-run]
```

Алгоритм:

1. Скачать манифест, проверить `manifest_sha256`. Скачать недостающие blobs, проверить SHA‑256 каждого. Любое несовпадение — отказ без изменений на диске.
2. Обеспечить base: если `head` отсутствует локально — `git fetch` из remote для `remoteBase`, затем импорт bundle (`git bundle verify` + `git fetch <bundle>`) для незапушенных коммитов.
3. **Целевая рабочая копия**:
   - по умолчанию: `git worktree add <repo>-pmi-<short-session> <head>` (на ветке `pmi/<session>`; если исходная ветка свободна и не существует локально — на ней);
   - `--in-place`: только если текущая рабочая копия **чистая** (`git status --porcelain` пуст). Иначе — отказ с кодом 2 и предложением worktree.
4. Записать файлы: для каждой записи манифеста — проверка конфликтов (§6), затем атомарная запись (временный файл + `rename`), mode, симлинки; `D` — удаление; индекс восстанавливается применением index‑patch (`git apply --cached`), с fallback на `git add` перечисленных staged путей.
5. Верификация: пересчитать SHA‑256 всех восстановленных файлов, сравнить `git status` с манифестом. Отчёт: восстановлено N, удалено M, исключено K (с причинами).
6. Записать метрику `workspace_recovery{result}` и событие в аудит.

`--dry-run` выполняет шаги 1–2 и проверку конфликтов, ничего не записывая.

## 6. Защита от потери данных и конфликты

Правило ТЗ: **никогда автоматически не перезаписывать более свежие изменения**.

| Ситуация | Действие |
|---|---|
| Восстановление в новый worktree | Конфликтов по определению нет |
| `--in-place`, рабочая копия грязная | Отказ |
| `--in-place`, HEAD получателя ≠ `head` snapshot | Отказ; предложить worktree |
| Файл получателя отличается от `baseBlob`, а snapshot тоже его меняет | Конфликт; файл не трогается, snapshot‑версия пишется рядом как `<file>.pmi-<snap>`; итог — код 2 |
| Snapshot старше другого snapshot той же сессии | Предупреждение и выбор (по умолчанию — самый свежий) |
| Сессия держится lease другого устройства | Restore разрешён только в новый worktree (чтение), resume — нет |

Дополнительно:
- Перед любым `--in-place` restore daemon автоматически делает **страховочный snapshot** текущей рабочей копии получателя (даже чистой — фиксирует HEAD).
- Workspace lease `branch:<repo>/<branch>`: пока сессия активна на ветке, другой клиент не может восстановить snapshot в эту же ветку `--in-place` без `--force` (maintainer).
- Секреты: файлы, попадающие под шаблоны `secret-filter` по содержимому или по имени (`.env*`, `*.pem`, `id_rsa*`, `*.key`), исключаются и попадают в `excluded` с причиной `secret`; `--include-secrets` требует явного флага и логируется. Blobs на сервере опционально шифруются ключом проекта (AES‑256‑GCM, ключ в env сервера) — включается в Phase 10.

## 7. Retention

- Сохраняются: все pinned (handoff), последний snapshot каждой незавершённой сессии, все snapshot за 7 дней, затем по одному в день до 30 дней.
- Завершённые сессии: snapshot удаляются через 30 дней после `COMPLETED`, если рабочая копия была закоммичена и запушена (проверяется по манифесту: нет `files` и нет `bundle`).
- GC blobs: `ref_count` = 0 и старше 24 ч. `pmi workspace gc` / серверный джоб. Удаление — только после проверки, что ни один манифест не ссылается на blob (транзакционно).

## 8. Резервное копирование

Blobs входят в `pmi-server backup` (архив тома + список хэшей). Restore сервера проверяет хэш каждого blob.

## 9. Опция `--via-branch`

Для команд, предпочитающих git‑нативный путь: snapshot дополнительно создаёт коммит `git stash create` → ветку `pmi/wip/<session>` и пушит её в remote. Отключено по умолчанию по причинам из §1.
